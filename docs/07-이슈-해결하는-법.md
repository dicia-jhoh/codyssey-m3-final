## 순서

1. **이슈를 끝까지 읽는다.** 목표 → 선행 → 고칠 파일 → 완료 기준 → 힌트. 모르는 게 있으면
   추측해서 고치지 말고 그 이슈에 댓글로 묻는다.
2. **최신 main 에서 새 브랜치를 만든다.** 이미 머지된 브랜치를 다시 쓰지 않는다 — 옛 기록 위에
   쌓여서 충돌이 나고, 머지된 브랜치는 정리하며 지운다.
   ```bash
   git switch main
   git pull
   git switch -c jeonggwan/152-retry-after     # <내 id>/<이슈 번호>-<무엇>
   ```
3. **고친다.** 이슈의 「고칠 파일」 위주로. 다른 파일도 고쳐야 했으면 PR 설명에 이유를 적는다.
   파일 이름을 바꿨으면 그 이름을 부르는 곳도 같이 고친다(`git grep 옛이름` 으로 찾는다).
4. **테스트를 돌린다.** 백엔드를 고쳤으면 테스트를 하나 이상 더하고 전부 통과시킨다.
   ```bash
   cd backend
   source .venv/bin/activate          # Windows: .venv\Scripts\activate
   pytest
   ```
   화면(`web/`·홈페이지)을 고쳤으면 브라우저로 직접 열어 보고 스크린샷을 PR 에 붙인다.
5. **완료 기준을 하나씩 체크한다.** 못 한 항목은 지우지 말고 PR 설명 「안 한 것」에 이유와 함께 남긴다.
6. **PR 을 올린다.** 아래 「PR 설명 틀」을 쓴다. 마지막 줄 `Closes #이슈번호` 가 있으면 머지될 때
   이슈가 저절로 닫힌다.
7. **내 기록을 남긴다.** PR 을 만들면 번호가 생긴다. 그 주소를 내 파일
   `content/members/<내 파일>.js` 의 `prs` 에 한 줄 넣고, 같은 브랜치에 커밋해 push 한다.
   홈페이지의 「PR N건」이 이 목록의 개수다.
8. **리뷰를 기다린다 — 직접 머지하지 않는다.** 머지 버튼이 보여도 누르지 않는다. 오주현이 리뷰를 남기고
   머지한다. 리뷰에서 나온 작은 결함은 오주현이 후속 PR 로 고치니, 그 PR 을 읽고 다음 이슈에 반영한다.

## PR 설명 틀

```markdown
## 무엇
이슈 #152 — 429 응답에 Retry-After 를 붙였다.

## 확인
- pytest 150 passed
- (화면이면) 스크린샷

## 안 한 것
- (없으면 「없음」) 못 한 완료 기준과 이유

AI 도구: (쓴 도구와 맡긴 일. 안 썼으면 「없음」)

Closes #152
```
